# Plan: Dolt branch-scaling study on CloudLab

## Context

Three hypotheses about Dolt as a single-machine branchable DB:

- **H1 Branching latency**: creating a branch gets slower as more branches exist.
- **H2 Data-op latency**: point/range reads and writes get slower as more branches exist.
- **H3 Interference**: concurrent load on many branches of one Dolt server degrades per-branch performance (and idle branches cost something).

The repo already drives Dolt through two adapters: `dolt` (Doltgres 1.4.0, Postgres wire, `dblib/dolt.py`) and `dolt_mysql` (Dolt 2.4.2 `sql-server`, MySQL wire, `dblib/dolt_mysql.py`). Both support every verb natively, commit refs, multi-ref exec and async pools. The user wants **both** flavours, driver **co-located** with the server on a CloudLab node, run **unattended to completion** with plots and a written conclusion.

Hosts: `.agent/cloudlab.md` lists 8 Wisconsin `c220g2` nodes, ssh key `~/.ssh/dassl_rsa`, user `JiyuHu23`. Probed node0 (`c220g2-010806`) and node1 (`c220g2-010812`): 2x Xeon E5-2660 v3 (20c/40t, 2 NUMA), 157 GB RAM, Ubuntu 22.04.2, root on a 63 GB partition of a **rotating** HDD (`sda`), an unused 447 GB Intel SSD (`sdc`), passwordless sudo, no go/dolt/uv/protoc installed. `~/dolt` on this machine is only the Dolt source checkout (no binary); the release binaries the repo's provisioning scripts pin (`scripts/remote/setup_dolt.sh` v2.4.2, `setup_doltgres.sh` v1.4.0) will be used instead, so results stay comparable with the repo's earlier EC2 runs.

## Experiment design

Data: CH-benCHmark at W=1 generated in-server by `macrobench.datagen.ch.seed_ch` (about 560k rows: stock 100k, item 100k, order_line ~300k, customer/orders 30k each), foreign keys skipped (`SchemaConfig.skip_foreign_keys`) so random INSERTs succeed. Benchmark table: `stock` (composite PK is handled by `select_random_key` via `dbh.get_pk_values`). Fresh database per run (`cleanup: true`), `dolt_gc` + purge of dropped databases between runs as the scripts already do.

Branch divergence: every setup branch gets `updates_per_branch = 100` untimed updates after creation, so branches hold distinct chunks (the realistic case). A small no-divergence control (updates 0) at N in {1, 64, 1024} for H2 checks whether any effect comes from refs alone.

Every hypothesis gets **both a latency and a throughput measurement**, all on the x axis "number of existing branches N":

| | Latency (single client, per-op p50/p95) | Throughput (concurrent clients, ops/s + p50/p95 under load) |
|---|---|---|
| H1 branching | E1-L: BRANCH_CREATE after an N-branch setup | E1-T: 16 threads creating branches concurrently after an N-branch setup |
| H2 data ops | E2-L: READ/RANGE_READ/INSERT/UPDATE/RANGE_UPDATE on one branch of N | E2-T: fixed 16x4 load on READ/RANGE_READ/UPDATE/INSERT, spread over N branches |
| H3 interference | E2-L and E2-T slopes vs N (idle-branch cost), plus E3 | E3: load grows with branches (aggregate scalability), and E2-T for B <= threads (same load over more branches) |

### E1 (H1): branch creation vs existing branches
- **E1-L (latency)**: `run_single_thread_bench.sh <backend> --generated-scale 1 1,2,4,...,1024 --operations BRANCH_CREATE --num-ops 10 --shape fan_out` and again `--shape spine`: after an N-branch setup, time 10 further creations. 11 N x 2 shapes x 2 backends.
- **E1-T (throughput)**: `run_throughput_bench.sh <backend> --generated-scale 1 --mode sync --sweep-branches --threads 16 --operations BRANCH_CREATE --num-ops 50 --branch-list 1,4,16,64,256,1024`: 16 threads each create 50 branches concurrently (800 creates per run) on top of N existing ones; branch creates/s and p50/p95 vs N (sync mode: verbs do not go through the async pool).
- Bonus, free: the `_setup.parquet` of every run holds one timed BRANCH row at every count 1..N (fine-grained latency curve).
- Corroboration: `python -m microbench.verbs --backend <b> --verbs branch --axes live,age --reps 10` (purpose-built, with storage deltas; `live` 1..128).

### E2 (H2): data ops vs N branches
- **E2-L (latency)**: `run_single_thread_bench.sh <backend> --generated-scale 1 --updates-per-branch 100 --table-name stock --operations READ,RANGE_READ,INSERT,UPDATE,RANGE_UPDATE 1,4,16,64,256,1024` (fan_out). 1000 point ops / 200 range ops per run (script defaults), on `setup_branch_N`. Add `--shape spine` at N in {1, 64, 1024} to see whether a 1024-deep chain differs from fan-out.
- **E2-T (throughput, fixed load)**: async mode, `--sweep-branches --threads 16 --concurrent-requests 4 --operations READ,RANGE_READ,UPDATE,INSERT --warmup-fraction 0.1 --updates-per-branch 100 --table-name stock --branch-list 1,2,4,8,16,64,256,1024`. For B <= 16 the same 64 in-flight ops are spread over more branches (interference between loaded branches); for B > 16 the extra branches are idle (cost of merely existing branches). Throughput from the summary JSON, p50/p95 per op from the rows.

### E3 (H3): scalability when load grows with branches
Async mode, same ops/table/divergence as E2-T: `--sweep-proportional --threads-per-branch 1 --concurrent-requests 4 --branch-list 1,2,4,8,16,32` (32 threads x 5 connections = 160, under Dolt's default 1000 max connections). Aggregate and per-branch throughput and p50/p95 vs B: if per-branch throughput falls or tail latency rises as more branches are loaded on the one server, that is interference; flat per-branch numbers up to the core count mean branches are isolated.
- Control (no divergence): E2-L and E2-T repeated with `--updates-per-branch 0` at N in {1, 64, 1024} to separate "refs exist" from "branches hold distinct data".

Expected signal: flat E1/E2 curves refute H1/H2 for Dolt; rising latency or falling throughput as B grows at fixed load (E2-T, B <= 16) or sub-linear aggregate scaling (E3) supports H3.

Runtime estimate per backend: E1 ~1.5 h, E2 ~2.5 h, E3 ~1 h, controls ~0.5 h (dominated by per-run seeding if ~2 min). The two backends run **in parallel on two nodes** (node0 = dolt_mysql, node1 = doltgres), one Dolt server per machine as requested, so total wall time is ~6 h. If the smoke test shows seeding > 60 s, implement the copy-from-seed fast path below before the sweeps.

## Machine setup (per node, scripted in `scripts/remote/setup_cloudlab_dolt.sh`, idempotent)

1. Append specs to `.agent/cloudlab.md` (CPU, RAM, disks, OS, kernel, which node runs which flavour, software versions, data-dir locations).
2. `mkfs.xfs /dev/sdc` and mount at `/mnt/ssd` (unused disk; root is HDD and would dominate latency). Dolt data dirs: `/mnt/ssd/dolt/databases`, `/mnt/ssd/doltgres/databases`.
3. Install Dolt 2.4.2 / Doltgres 1.4.0 release binaries as in `setup_dolt.sh` / `setup_doltgres.sh` but bound to 127.0.0.1, `User=$USER` (the scripts hardcode `ubuntu`), data dir on the SSD, and run under `numactl --cpunodebind=0 --membind=0` (apt `numactl xfsprogs`); the driver runs on NUMA node 1 so the client does not steal the server's cores. Dolt's `listener.max_connections` already defaults to 1000 (docs). Start `dolt sql-server` with a `config.yaml` that sets `behavior.auto_gc_behavior.enable: false` so automatic GC (which blocks writes and drops connections) cannot fire mid-run; GC happens only between runs where the scripts already call `dolt_gc` / purge. Doltgres gets the same `data_dir`/`listener` keys via its `config.yaml`.
4. Driver: rsync the repo (excludes as in `setup_driver.sh`), apt `protobuf-compiler rsync`, install uv, `uv python install 3.13`, `uv sync`.
5. Remote `.env`: `DOLT_MYSQL_HOST=127.0.0.1`, `DOLT_MYSQL_DATA_DIR=/mnt/ssd/dolt/databases`, `DOLT_HOST=127.0.0.1`, `DOLT_DATA_DIR=/mnt/ssd/doltgres/databases` (absolute: `dolt.py:26` defaults to `~/doltgres/databases`, which is wrong here).
6. Everything runs under `nohup`/`setsid` with logs under `run_stats/dolt_scaling_<date>/logs/` so an ssh drop does not kill a sweep; a `progress` one-liner checks status.
