## Goals

1. **Split for the cross-zone experiment** (rerun of experiments 4/5/8 on this cluster). Recommended 8/8, one
   subnet per zone, mirroring the 22 Oct two-zone cluster:
   - storage zone: s0 storcon + its Postgres + broker + seed compute (Doltgres server when Neon is stopped);
     s1-s3 one safekeeper each (exp 5: writes were safekeeper-bound); s4-s7 pageservers (1/2/4-shard sweeps; with
     25 GbE the pageserver should become CPU-bound instead of the 1 GbE cap seen in exp 5).
   - compute zone: c0 client (64 GB avoids exp 5's client OOM at N = 1,024); c1-c7 compute agents (~15 GB of
     computes per node at N = 1,024, 70 cores vs 56 on the r320s).
   - fallback 6/10 if no 4-shard sweep is wanted.
2. **Probe the hardware** of all 16 nodes: CPU model/topology/NUMA, memory, disks (model, free space, fio if
   useful), NICs (`ip -br a`, `ethtool`, link speed, which interface is control vs experimental), kernel and OFED.
3. **Test RDMA between nodes**: `ibv_devices` / `ibv_devinfo` / `rdma link`, RoCE version and GID table, then
   perftest (`ib_write_lat`, `ib_read_lat`, `ib_send_lat`, `ib_write_bw`, `ib_read_bw`) for same-subnet and
   cross-subnet pairs, compared with TCP (ping, `tcprtt.py`, iperf3).
4. **Cross-host networking plus an artificial cross-subnet delay**, like `.agent/network-probe-2026-10-29/`
   (`scripts/az_netem.sh apply 400`: prio root qdisc, netem delay only for the other zone's addresses, ~1 ms
   cross-zone RTT, no jitter). Things to settle first:
   - the two VLANs probably do not route to each other (as on 29 Oct); cross-zone traffic then needs a third LAN
     spanning all 16 nodes, a router node, or the public control network (check its speed on xl170 first;
     on c220g* it was 1 GbE). Re-run the 29 Oct probe (`probe.sh`, `summarize.py`) before and after the delay.
   - choose the delay: ~1 ms (AZs in one region, 29 Oct) or ~39 ms (Wisconsin-Utah, exps 4/5/8).
   - at 25 GbE netem needs a large `limit` (bandwidth-delay product ~3 MB at 1 ms, ~120 MB at 39 ms; default
     1,000 packets will drop) and larger `net.core.{r,w}mem_max` / `tcp_{r,w}mem` for long delays.
   - netem is lost on reboot; record `az_netem.sh status` output with the probe.
5. **Question: does the added latency affect RDMA performance?** Expectation to verify:
   - RoCE traffic is posted by the NIC directly and bypasses the kernel stack, so `tc netem` on the host most
     likely does not delay RDMA at all. Check by running `ib_write_lat` cross-subnet with and without netem.
   - Delaying RDMA for real needs a delay node in the path (or switch support). If it is delayed, latency grows by
     the added RTT, one-outstanding reads slow by the same amount, and bandwidth holds only if the in-flight data
     (QP depth x message size) covers 25 Gbit/s x RTT; RoCE also reacts badly to netem-style loss.
